# Разработка и тесты

Как работать с кодом [[Архитектура WebStudio|WebStudio]] и что тестировать.

## Стек тестирования

**Vitest + React Testing Library** (`@testing-library/react`, `@testing-library/user-event`).

- Тестовые файлы — рядом с исходником: `ServiceCard.tsx` + `ServiceCard.test.tsx`.
- `src/tests/setup.ts` — глобальный setup (jest-dom matchers и т.п.).
- `src/tests/utils/renderWithProviders.tsx` — обёртка рендера с `QueryClientProvider` + `RouterProvider`. Всегда использовать её, а не голый `render`.

## Что мокировать

**Мокировать `api.ts` домена** — не `supabase` напрямую.

```ts
// ✅ правильно
vi.mock('@/features/services/api', () => ({
  listServices: vi.fn().mockResolvedValue([...])
}))

// ❌ неправильно — мокировать supabase-клиент напрямую
vi.mock('@/lib/supabase', ...)
```

Причина: тесты проверяют поведение через тот же публичный интерфейс, что использует приложение; детали Supabase-запроса — не наша забота в юнит-тесте.

## Что тестировать (приоритеты)

1. **Zod-схемы** (`schemas.test.ts`) — граничные случаи валидации, обязательные поля, трансформации.
2. **React Query хуки** (`useCreateService.test.tsx` и т.п.) — успешный путь, ошибка, инвалидация кеша.
3. **Критичные формы** — `ContactForm` ([[Домен Лиды]]), форма создания услуги.
4. **`ProtectedRoute`** — редирект без сессии, рендер `<Outlet>` с сессией.

Снапшот-тесты — не использовать (хрупкие).

## Конвенции в тестах

- `userEvent` предпочтительнее `fireEvent` (ближе к реальному взаимодействию).
- Тестировать **поведение** (что видит пользователь), не внутренности компонента.
- Каждый тест — независимый: `beforeEach` сбрасывает моки.

## Workflow разработчика

```bash
npm run dev          # dev-сервер с HMR
npm run test         # Vitest watch-режим (в фоне)
npm run test:ui      # Vitest UI в браузере
```

**Перед пушем:**
```bash
npm run typecheck && npm run lint && npm run test:run
```

TypeScript `strict: true` — `any` запрещён, использовать `unknown` или конкретный тип. Все импорты через алиас `@/` (не относительные `../../`).
